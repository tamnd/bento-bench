# Benchmark run 2026-07-02

This is a full run of the harness against the current bento AOT path, timed on an Apple Silicon laptop.
bento is measured the way the README describes: each workload is compiled to a native Go binary with `bento build` and the binary is what gets timed.
Bun and Deno are compiled the same way with `bun build --compile` and `deno compile`.
Node stays the interpreter reference.

Run settings: 12 timed runs, 3 warmup, a 20s soft budget per cell.
bento was built from `tamnd/bento` at `645e364` (branch `feat/aot-build-console-log`), which lands the string split and plain-literal regex replace lowering, so the strings workload compiles for the first time.

## What this run shows

bento already wins the numbers the compiler was built to move.
It is the fastest runtime on `fib`, `mandelbrot`, `readwrite`, and `hello`, it is the leanest on peak memory in every workload except one, its cold start is the lowest of the four at 3.0ms, and its binary is 2.8MB against Bun's 58.2MB and Deno's 75.4MB.
On the tight numeric loops the story is clear: `mandelbrot` is 4.9ms against Bun's 14.5ms, and it holds 4.1MB of memory where the JavaScript runtimes hold 26MB to 74MB.

The string workloads are where bento is still slow, and one of them is badly slow.
`strings` runs in 7.40s and holds 571.5MB, which is not a close race, it is an algorithmic problem in the value string path (split, join, and replace over a 20000-piece array, thirty times).
`replace`, `templates`, `coercion`, `fromcharcode`, and `numfmt` are all a few times slower than the fastest other runtime for the same reason: the string and formatting helpers allocate more than they should.
These are the target of the next work, the value-runtime optimization pass, and this report is the baseline it will be measured against.

`roundtrip` fails to compile because the JSON stringify and parse path and the dynamic value machinery it needs are not lowered yet.
That is honest in the table as `fail` rather than a number earned a different way.
